# エラー・回復・再試行

## エラーを分類する

期待する失敗を`Data.TaggedError`等で表し、呼び出し側が判断できる最小の安全なフィールドを持たせる。シリアライズするエラーにはSchemaベースの定義を検討し、導入版のAPIを確認する。全エラーを`Error`や文字列に潰さない。

- 期待する失敗: 型Eで扱い、必要なタグのみ`catchTag`/`catchTags`で回復する。
- defect: プログラムの不整合など。一般的な外部障害へ置換して隠さない。
- interruption: キャンセルという終了理由。成功や再試行可能な通信障害と混同しない。

v4の`Effect.catch`は型付きエラー全体を捕捉する。汎用fallbackを置く前に、すべてが同じ回復条件を持つか確認する。`orDie`で回復可能な失敗をdefectへ逃がさない。`catchCause`を使うならdefect・中断を保持する方針を明示する。

`Effect.result`は期待する失敗をResultへ移し、defectと中断は残す。部分成功を集める用途で使えるが、その中の失敗を評価して完了状態を決める。`option`は理由が不要で「失敗=不在」と言える場合だけ使う。

## Promiseアダプター

`Effect.tryPromise({ try: signal => sdkCall({signal}), catch: classify })`で呼び出しを遅延し、最小のI/O境界で拒否を分類する。既に開始したPromiseを閉じ込めない。`Effect.promise`の拒否はdefectになるため、失敗が想定されるSDKに使わない。

- fetchはHTTP 4xx/5xxだけではrejectしない。status、契約済みのprovider code、応答Schemaを別に評価する。
- 生のSDKエラーのmessage/cause/bodyを公開型へ丸ごと保存しない。内部診断も安全なフィールドを許可リスト化する。
- `tryPromise`へ全業務処理をまとめるとバグまで外部障害へ変換する。SDK呼出しとドメイン計算を分ける。
- Signal非対応のSDKではfiber中断後も操作が継続し得る。制約を明記し、特に書込結果を未反映とみなさない。

## retry/timeoutの設計手順

1. 再試行してよい操作とタグを特定する。認証不備、入力不備、無料枠切れ、予算超過は除外する。
2. 一回の「試行」に含める処理を決める。複数副作用を持つworkflow全体にretryを掛けない。
3. 最大回数と総時間を決める。v4の`times: n`は初回に加えてn回。`schedule`は待機・backoff・jitterを定義する。
4. 毎回の送信前に共有予算を原子的に確保する。初回も対象とする。複数fiber・再配信・SDK内retryを合算する。
5. Retry-Afterを尊重し、総期限を超えるなら終了か永続的な再開へ移す。上限に収めるため待機を短縮しない。
6. timeoutをretryの内側へ置くと各試行、外側へ置くと全体の期限となることを踏まえて配置する。中断不能領域や非協調SDKでは指定時間ぴったりに終了する保証がない。
7. 「書込み後に応答喪失」は結果不明とする。冪等キー・結果照合などで安全性を証明できる場合だけ再送する。Effectのretry自体はexactly-onceを保証しない。

HTTPの固定エラーコードへの変換、Queueの配送判断、業務上の部分結果の記録は別の境界で行う。失敗をログしてackするだけで完了扱いにしない。
