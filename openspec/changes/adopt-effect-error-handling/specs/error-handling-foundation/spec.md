# Error handling foundation

## Purpose

Netzの今後のMVP実装が無料枠・共通予算・重複防止を守って失敗を扱えるよう、型付きの回復判断とHTTP境界の安全な応答を提供する共通基盤の契約を定義する。実際のハンドラーへの接続は別の実装段階として扱う。

## ADDED Requirements

### Requirement: 失敗の分類と再試行制限

エラー処理基盤は認証・設定・入力・無料枠・予算・一時障害・ページ取得・保存結果不明を区別しなければならない（MUST）。枠切れと予算超過は停止、保存不明は照合として判断し、一時障害は安全性・残り回数・予算を満たす場合だけ再試行候補としなければならない（MUST）。

#### Scenario: 無料枠と予算の停止

- **WHEN** 残り再試行回数があっても枠切れ・予算超過を渡す
- **THEN** 再試行ではなく停止を返す

#### Scenario: 書き込み結果不明

- **WHEN** 保存結果不明を渡す
- **THEN** 再試行条件にかかわらず照合を返し、書き込みを実行しない

#### Scenario: 再試行の条件

- **WHEN** 一時障害を渡す
- **THEN** 安全な読み取りまたは未反映確認済み書き込みで、回数と予算と待機値が適切な場合だけretryを返す

### Requirement: 安全なHTTP境界

HTTP用の実行境界は型付き失敗・defect・中断を区別し、固定のエラーコードと非成功のHTTPステータスへ変換しなければならない（MUST）。内部例外・cause・資格情報・上流本文を応答に含めてはならない（MUST NOT）。成功レスポンスは保持しなければならない（MUST）。

#### Scenario: 想定内の失敗

- **WHEN** 認証・設定・入力等の型付き失敗を実行する
- **THEN** 対応した失敗ステータスと固定コードを返し、no-storeを設定する

#### Scenario: defectと中断

- **WHEN** 予期しない例外または中断が起きる
- **THEN** 成功や通常の調査完了と扱わず、安全な内部エラーまたは中断応答を返す

### Requirement: 回復判断と副作用の分離

回復判断は配送ack・再送・Notion保存・永続予算更新を自動実行してはならない（MUST NOT）。呼び出し側が永続状態と予算を確認して実行する契約とし、基盤の導入だけで既存ハンドラーが保護済みと扱ってはならない（MUST NOT）。

#### Scenario: 回復判断だけを取得

- **WHEN** エラーからretry・stop・reconcile等の判断を取得する
- **THEN** 判断値だけを返し、ネットワーク呼び出しやQueue操作を起動しない
